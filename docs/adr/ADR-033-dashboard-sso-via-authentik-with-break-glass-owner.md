# Dashboard SSO via Authentik with a Break-glass Owner

## Status
Accepted

Proposed and accepted by the owner on 2026-10-18. This record amends ADR-020
(operator session boundary): it adds a second way to obtain the same session
and three public routes. It does not change ADR-020's session model, TTLs,
CSRF rules or deny-by-default stance. Related: ADR-004 (parity), ADR-006
(explicit planned changes), ADR-015 (secure first claim), ADR-021 (secret
store) and ADR-014 (first-party catalog).

## Decision
Once the appliance's own Authentik is installed from the catalog, the owner
may sign in to the Homestead dashboard with Authentik. The local `owner`
administrator account is permanent and is the break-glass path: it can never
be removed, disabled or made dependent on Authentik, and local password login
always works whether or not Authentik is reachable.

### Sign-in flow
- OIDC authorization code with PKCE (S256), `state` and `nonce`, Homestead as
  a confidential client of the appliance's Authentik (the callback is
  server-side, so a client secret can be kept). The client secret is
  generated by Homestead and stored sealed under ADR-021; it never appears in
  desired YAML, plans, audit entries or API responses.
- The login page offers "Sign in with Authentik" beside the local password
  form once SSO is configured **and** an identity is linked. The button is
  shown from local state only, with no probe of Authentik, so a dead
  Authentik cannot hide or slow the login page. A failed attempt returns to
  the login page with a fixed error code and the sentence "Authentik did not
  answer. Use your local password."
- A successful callback mints the same Homestead session as a password login
  (ADR-020): `HttpOnly` cookie, per-session CSRF token, same idle and
  absolute TTLs, same revocation. The session records its method
  (`password` or `oidc`) for audit and for the step-up rule below.
- Public routes added to the ADR-020 allowlist (only these three):
  `GET /api/v1/sso/options` (whether SSO is offered; no secrets, no issuer
  internals), `GET /api/v1/sso/login` (starts the flow) and
  `GET /api/v1/sso/callback`. All three answer 404 before claim and while SSO
  is not configured and linked. Every other SSO route is session-class.

### Linking
- Only the owner identity is linkable, with exactly one link (issuer plus
  `sub`). The mapping key is the pair `(issuer, sub)`. Email, username and
  group claims are never used to map or to grant anything.
- **No auto-provisioning.** An Authentik user whose `(issuer, sub)` is not
  the linked pair is refused, audited and never creates a Homestead
  administrator, whatever Authentik's own policies say.
- Linking and unlinking are owner actions that require a fresh local
  password (re-authentication within the request, not the cached session) and
  are audited with the actor, method and Authentik subject (not tokens).
  The link ceremony: the owner, authenticated and re-authenticated, creates a
  server-side single-use link intent (10 minute expiry, bound to the admin and
  the state value); the browser then runs the same OIDC flow with
  `prompt=login`; the callback consumes the intent and records the pair. The
  intent is looked up by `state`, not by the session cookie, because that
  cookie is `SameSite=Strict` and is not sent on the cross-site return from
  Authentik.
- Unlinking removes the pair and revokes the owner's OIDC-method sessions.

### Configuring the Authentik side
Homestead configures Authentik through the usual plan, review, approve flow
(ADR-006), never as a side effect of install:

1. The owner creates an Authentik API token and gives it to Homestead. It is
   stored sealed under ADR-021 under a named secret. By default it is used
   once and forgotten after apply; keeping it for later reconfiguration is an
   explicit opt-in. The review states plainly what the token can do in
   Authentik, because Authentik tokens are not narrowly scoped.
2. Homestead builds a plan: one OAuth2/OIDC provider (confidential, strict
   redirect URIs, scopes `openid profile email`, a named signing key, stable
   `sub` mode) and one application bound to it. The plan lists every object
   to create or change, the redirect URIs, and what it will **not** touch
   (users, groups, flows, policies, other applications).
3. The owner approves the exact plan (an approval binds to the plan digest, as
   exposure and TLS approvals do); apply is an operation with audit entries.
   Apply is idempotent and re-plannable; drift is shown, not auto-fixed.

### Origins and redirect URIs
The redirect URIs are pinned to the appliance's own origins, computed from
desired state: the local HTTPS name and, when configured, the public hostname,
each with the path `/api/v1/sso/callback`. The start handler selects the URI by
exact match of the request's origin against that set and refuses anything else;
it never builds a URI from an unvalidated `Host` or `X-Forwarded-*` header.
Authentik is told the same exact strings (no wildcards, no regex mode).

### Token validation (back channel)
The callback performs the code exchange from the daemon. It validates the ID
token: signature against the provider's JWKS (RS256 or ES256 only, `none` and
HMAC refused), `iss` equal to the configured issuer string, `aud` containing
the client id (and `azp` equal to it if present), `nonce` equal to the stored
value, `exp`, `iat` and `nbf` with a 2 minute skew allowance, and a state value
that is single-use with a 10 minute lifetime. The state, nonce and PKCE
verifier live in a short-lived `HttpOnly`, `Path=/api/v1/sso`, `SameSite=Lax`
cookie plus a server-side record, and are consumed on first use. When Authentik
is on the same appliance the daemon reaches it over the local path and trusts
the appliance CA (ADR-030), so the exchange does not leave the machine.
Discovery metadata is read from the configured issuer only and the issuer is
fixed at configuration time, not taken from a response.

### Local login keeps its hardening
Password lockout (five failures in ten minutes, 15 minute lock), uniform
failure answers and password-change revocation are unchanged. OIDC callbacks
are rate-limited and aggregated in the audit log like boundary rejections. A
locked local account does not block SSO and SSO success does not clear local
lockout counters.

### Step-up for SSO sessions
Because an SSO session is only as strong as Authentik, an `oidc`-method
session must present the local password again (fresh re-authentication) for
the most damaging actions: link, unlink, SSO reconfiguration, secret re-key,
and the backup recovery identity export. Password sessions keep today's
behaviour for those that already have a confirmation. The slice enumerates the
exact routes; ADR-020's route table gains an annotation, not a new class.

### CLI
`homesteadctl login` keeps minting a bearer token from the local account
(`POST /api/v1/sessions`); nothing about CLI authentication depends on
Authentik. OIDC for the CLI (a device authorization grant or a
browser-assisted loopback flow) is **deferred**: Authentik can offer a device
flow, but it needs a second provider and flow configured, a polling endpoint
on the daemon and a new bearer-minting path, which is more surface than this
record justifies. It is recorded in `docs/DEFERRED.md`. CLI parity for the
configuration itself holds under ADR-004: `homesteadctl sso status|plan|approve|apply|link|unlink|disable`.
`sso link` mints the single-use link intent after a password prompt and prints
a URL to open in a browser; the browser completes the ceremony.

## Context
Authentik is an optional catalog package (S201) and its manifest declares
`sso: class: unsupported` because it is the identity provider, not a consumer.
The dashboard session model is local administrators only (`internal/auth`).
Owners who already run Authentik for their apps want one sign-in, but the
appliance must stay recoverable when the identity provider is down, which is
exactly when an owner most needs the dashboard.

## Security consequences
- **Authentik compromise.** Anyone who controls Authentik (an Authentik admin,
  a stolen token, a bad upgrade) can mint a valid ID token for the linked
  subject and so obtain an owner session. This is inherent to delegating
  sign-in and is why: only one `(issuer, sub)` maps; SSO is opt-in per link;
  step-up applies to the destructive routes; the owner can unlink or
  `sso disable` from the local account or CLI at any time; and the review
  states this trade-off before the owner approves.
- **Circular dependency.** Authentik runs on the appliance Homestead manages.
  If Authentik is down, mis-upgraded or removed, local login is unaffected.
  Uninstalling Authentik marks the link dormant and the button disappears.
- **Subject reuse.** A deleted and recreated Authentik user gets a new `sub`
  and no access; `(issuer, sub)` is never reassigned by email.
- **Redirect and mix-up attacks.** Strict pinned URIs, a single configured
  issuer, `iss` check and single-use state defeat open redirects, code
  injection and issuer confusion.
- **Logout.** Homestead logout ends the Homestead session only. Ending the
  Authentik session (RP-initiated logout) is deferred.
- **Back channel secrets.** Client secret and optional API token are sealed
  under ADR-021 and excluded from plans, logs and exports.

## Alternatives considered
- Replace local login with Authentik: removes the break-glass path; rejected.
- Trust a reverse-proxy header from Authentik's outpost: moves trust to
  anything that can reach the dashboard port and fails open; rejected.
- Map by email: mutable and attacker-influenced at the IdP; rejected.
- Auto-create administrators from Authentik groups: widens the owner set
  beyond what the claim established (ADR-015); rejected.
- Public client without a secret: possible, but the callback is server-side
  so a confidential client is strictly stronger.

## Amends
This record amends ADR-020; ADR-020 carries a pointer to it.

## Consequences
- The local `owner` account stays permanently; no code path may delete,
  disable or SSO-gate it, and local login is never made conditional on
  Authentik state.
- Exactly three SSO routes join the public allowlist; each has a
  route-classification entry and a parity row.
- One link, owner only, keyed by `(issuer, sub)`; no auto-provisioning.
- Link and unlink require a fresh local password and are audited.
- Authentik is configured only through a reviewed, digest-bound, audited plan.
- OIDC for the CLI is deferred; the bearer path stays local-account only.
- Implementation must preserve this boundary.
- Changes require a superseding ADR.
