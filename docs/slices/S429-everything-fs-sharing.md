# S429: Everything FS sharing

ADR-058 section 3 ("fs") and the SDK surface. Depends on S425, S426, S428. Bridge and shim only; no daemon, API, CLI or dashboard change, so no PARITY change. The Circuits and Parametric UI stay hidden (S439, S440).

## Scope
`fs.share`, `fs.unshare`, `fs.getShares`, `fs.listShared`, and file operations on the reserved `~shared/<id>/...` paths: read (`get`), `put`, `stat`, `readdir`, `rename`, `delete`, `deletetree`. The call shapes come from Circuits `src/app/share.js` and Parametric `src/app/share.ts`: `fs.share(path, {username}, mode)` -> `[{isNew}]`, `fs.getShares(path)` -> `[{holder, mode, inheritedFrom}]`, `fs.listShared({cursor, limit})` -> `{items: [{path, name, owner, mode, modified}], cursor}`, `fs.unshare` -> `{revoked}`.

## Design as built
- `internal/everything/fssharing.go`. Operations `fs.share`, `fs.unshare`, `fs.getShares`, `fs.listShared` go through the existing POST data route (so Origin, Sec-Fetch-Site, content type and CSRF apply). The request fields are the S428 ones: `key` (path), `recipient`, `access`, `limit`, `cursor`.
- Reused from S428, not duplicated: the `-sharing` switch (`fs_sharing_disabled`, 403, when off), the 60 per hour attempt limiter (one counter per person per app, shared with `kv.share`; `fs.unshare` counts too, because it takes a typed name), `fresh` (24 hour session recheck on `fs.listShared` and every `~shared` file operation), `accessOf` (`manage` -> `bridge_unsupported`), `pageGrantRows` cursors, and a new `grantErr` mapper that kv.share now also uses.
- Errors (JSON `{error}`): `user_does_not_exist` (unknown, purged, other-app-only, malformed, over-long names are byte-identical), `cannot_share_with_self`, `invalid_recipient` (email or empty), `bridge_unsupported`, `invalid_argument`, `path_not_found` (sharing a path the caller does not have), `share_limit`, `share_rate_limited`, `share_read_only` (422, only to the proven recipient). `fs.unshare` of an unknown name and of a name with no share both answer `{revoked: 0}`, so it is not a name oracle. `fs.getShares` is owner-only (own scope) and lists live grants on the path and, with `inheritedFrom`, on a parent folder.
- `fs.share` grants a file exactly, or a folder as a prefix (decided by `Stat`). Repeating it updates the mode and keeps the id (`isNew: false`).
- `~shared` is reserved: `validate` rejects it as a first segment of any file key (so `Put`, `PutBatch`, import and rename targets refuse it); the handler routes such a key to the grant path instead. `listShared` returns `~shared/<id>` for a folder and `~shared/<id>/<file name>` for a file (so apps that read the extension from the path keep working); a file grant also accepts the bare `~shared/<id>`. Folder grants take any clean relative path under `~shared/<id>`.
- Every failure to prove the grant (unknown id, someone else's, other app, kv handle, revoked, purged owner or recipient, `..`, `.`, `//`, backslash, trailing slash, sibling prefix) is the same plain 404, like a missing file.
- Single-file grants: read, and overwrite with `write`; never create elsewhere, delete or rename. Folder grants with `write`: create, overwrite, delete, `deletetree` and rename inside the folder (same folder only, never over a file; both names must be under the same grant id); never the folder itself. A read grant refuses all of these with `share_read_only`.
- Deletion is permanent revocation (like read links): `Store.Delete`, `DeleteTree` and `Rename` of a file revoke, in the same transaction, the owner's fs grants on that file and (tree delete) at or under the deleted folder. A rename revokes rather than moves the grant (the ADR is silent; revoke is the safe choice). Deletes by a recipient through a folder grant run the same store code. Re-creating the path never revives a share; the folder grant itself is revoked only when the folder is tree-deleted.
- Recipient writes call `Put` with the owner's scope, so the owner's person and app quotas pay.
- `listShared` items: `path, name, owner (username), mode, modified (ms, as stat), size, is_dir`; items whose file the owner removed are skipped.
- Shim: `fs.share/unshare/getShares/listShared` as above (the `{email}` form fails locally with `invalid_recipient`; the default mode is `read`); `~shared` paths work with the existing `fs.read/write/stat/readdir/rename/delete` because paths pass through unchanged.

## Tests
`internal/everything/fssharing_test.go`: file round trip (read, overwrite, stat, no copy, owner quota, no delete/rename/sibling access), read-only file, folder grant (readdir, stat, nested read, escapes, quota charge, create, rename rules, delete, deletetree, folder itself protected, inherited `getShares`, read grant refusals), delete/rename/tree-delete revocation (incl. recipient deletes), reserved `~shared`, uniform and validated errors, rate limit and grant limit, 24 hour recheck, cross-person, cross-app, kv/fs id confusion, purged owner, sharing off, listShared paging and vanished files. `sharing_test.go`: CSRF on the new operations. Gate bridge mode 10/10 (new off-by-default checks and a stubbed-fetch test of the call shapes); a Projects browser check; Python tests updated for the shim surface.

## Unproven
No live OIDC two-person run; real Circuits and Parametric code does not exercise sharing (UI hidden). No package turns `-sharing` on.
