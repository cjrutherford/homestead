# S286 — Dashboard sign-in with Authentik

## Goal
Let the owner sign in to the dashboard with the appliance's own Authentik while the local `owner` account remains a permanent break-glass path.

## Dependencies
S285 (Authentik installs through the new wizard), S283 (work orders and states). ADR-033 (Accepted 2026-10-18) governs.

## Scope
Implement only the functionality required for this slice. Preserve all accepted ADRs and customer-ownership guarantees. Do not pull deferred features into scope without an ADR and slice update.
Governed by ADR-033, which amends ADR-020. In scope: OIDC login, link/unlink, Authentik-side configuration by plan/approve, login page, CLI configuration parity. Out of scope and recorded in `docs/DEFERRED.md`: OIDC login for the CLI (device or browser-assisted flow), RP-initiated logout from Authentik, more than one linked identity, SSO for non-owner administrators, disabling local password login.

## Acceptance Criteria
- Dashboard sign-in with Authentik implemented and documented
- OIDC flow: authorization code with PKCE S256, `state` and `nonce`, confidential client; `GET /api/v1/sso/login` starts, `GET /api/v1/sso/callback` finishes; the callback mints the standard ADR-020 session (cookie, CSRF, TTLs) tagged `oidc`
- ID token validation: JWKS signature (RS256/ES256 only; `none` and HMAC refused), exact `iss`, `aud` and `azp`, `nonce`, `exp`/`iat`/`nbf` with 2 minute skew, single-use state with 10 minute life, issuer fixed at configuration time; back channel trusts the appliance CA (ADR-030) and stays on the appliance when Authentik is local
- Redirect URIs pinned to the appliance's own origins (local HTTPS name, public hostname when configured) by exact match from desired state; a forged `Host` or `X-Forwarded-*` is refused; the same exact strings are configured in Authentik
- No auto-provisioning: an unlinked `(issuer, sub)` is refused and audited and creates nothing; email, username and groups never map or grant
- Authentik configuration through plan, review, approve (digest-bound approval), apply as an operation: API token stored sealed per ADR-021 and used-once by default (opt-in to keep); plan lists the OAuth2 provider and application to create or change and what is left untouched; apply idempotent; client secret generated by Homestead and sealed, never in YAML, plans, audit or responses
- Link and unlink: require a fresh local password re-authentication, create a single-use server-side link intent (10 min, bound by `state`, not the Strict session cookie), run the flow with `prompt=login`, are audited with actor, method and subject; unlink revokes OIDC-method sessions; one link, owner only
- Step-up: an `oidc` session must re-enter the local password for link, unlink, SSO reconfigure, secret re-key and backup identity export; the exact route list is declared in code beside the route classes and tested
- Login page: "Sign in with Authentik" shown from local state only (no Authentik probe) beside the local password form; Authentik errors return to the login page with fixed codes and the message "Authentik did not answer. Use your local password."; a Settings/Sign-in page shows status, link, unlink and the configuration plan flow
- Lockout and rate limits: local lockout (five failures in ten minutes, 15 minute lock) unchanged; OIDC callbacks rate-limited and aggregated in audit; local lockout does not block SSO and SSO does not reset local counters
- CLI behaviour: `homesteadctl login` and bearer sessions unchanged and local-account only; new `homesteadctl sso status|plan|approve|apply|link|unlink|disable`; `sso link` prompts for the password, mints the link intent and prints a URL to finish in a browser; CLI OIDC login is not implemented (deferred, ADR-033)
- Boundary classification (ADR-020): in `internal/server/boundary.go` `routeClasses`, public: `GET /api/v1/sso/options`, `GET /api/v1/sso/login`, `GET /api/v1/sso/callback` (404 before claim and unless SSO is configured and linked); session: `GET /api/v1/sso`, `POST /api/v1/sso/plan`, `POST /api/v1/sso/approve`, `POST /api/v1/sso/apply`, `POST /api/v1/sso/link`, `DELETE /api/v1/sso/link`, `DELETE /api/v1/sso`; the route-classification test is green and the public allowlist test names exactly the three new routes
- `docs/PARITY.md`: a row per route with its CLI command and dashboard surface (public flow routes marked as browser-protocol routes with the CLI equivalent noted); the parity test is green
- Tests with a fake OIDC provider (in-process discovery, JWKS, token endpoint): happy path; wrong `iss`, `aud`, `nonce`, expired, not-yet-valid, skew edge, bad signature, `alg: none`, replayed or unknown `state`, expired state, redirect mismatch; unlinked subject refused with nothing created; link/unlink with and without fresh password; intent single use and expiry; step-up; Authentik unreachable leaves local login working; fake Authentik admin API for plan, approve, apply, idempotence and token not retained; secrets absent from plans, audit and responses; lockout interaction
- Dashboard specs: login page both options, SSO error codes, Sign-in page states, link and unlink with re-auth dialog, plan/approve flow
- KVM on VM 2 with a real Authentik installed through the S285 wizard: configure by plan/approve, link the owner, sign in with Authentik, confirm the session behaves like a password session (CSRF, logout, expiry), verify refused unlinked user, then **break Authentik** (stop its containers, and separately break the issuer config) and prove the local password login still works and the login page stays usable; unlink; leave VM 2 as found; transcript in `docs/DEVELOPMENT.md`
- Automated tests cover primary behavior
- Main build remains green
